# 本番移行・復旧手順

2026-09-14の本番切り替えは実施済みです。実際の構成と検証結果は[本番移行記録](DEPLOYMENT-20260914.md)を参照してください。以下は初回移行の前提と、今後の再移行・復旧に関する手順です。

## 初回移行前の状態（履歴）

- 対象Cloud Run：`topform-booking-bot` / project `topform-booking-bot` / region `asia-northeast1`。
- 旧リビジョン：`topform-booking-bot-00106-m54`。監査時点でトラフィック100%。
- 最大3インスタンス、ローカルSQLite、永続ボリュームなし。
- Cloud SQL Admin API・Firestore APIは未有効。この時点では永続DBなし。
- キャンセル待ちSchedulerはPAUSED。再開していない。

## 移行の前提

1. 共有PostgreSQLを用意する。推奨候補は同一リージョンのCloud SQL PostgreSQL 16。料金、容量、可用性、バックアップ方針は作成前に決定する。既存の外部PostgreSQLが使える場合はそれでもよい。
2. 旧環境の未処理仮予約を回収・照合する。Cloud Runのローカルファイルはインスタンスごとに異なるため、一つのSQLiteのコピーだけで全件回収できたとみなさない。スタッフへの受付通知とカレンダーも照合する。旧環境へ自動エクスポート手段は実装されていないため、回収方法と受付を止める時間帯の決定が必要。
3. 顧客マスタの実際のタブ名と同姓同名・短い登録名、予定タイトルの店舗表記を確認する。曖昧な利用者はカレンダーへのID関連付けを行う。

## データ移行

読み取り検証（変更しない）:

```sh
venv/bin/python scripts/migrate_database.py /secure-backup/topform_line.db
```

空のPostgreSQLへコピー:

```sh
# DATABASE_URLは安全な方法で環境変数へ設定する。
venv/bin/python scripts/migrate_database.py /secure-backup/topform_line.db --apply
```

移行は通知を送信しません。無効な日時やJSONがあれば中止します。既存データを勝手に修正せず、スタッフと照合してから再実行してください。ターゲットが空でなければインポートを中止します。

## 構成

Secret Managerなどで`DATABASE_URL`と32文字以上のランダムな`ADMIN_API_TOKEN`を用意します。DB接続文字列・LINE資格情報をコマンドログ、Git、フロントエンドへ書かないでください。`CUSTOMER_SHEET_NAME`、既存LINE/Google設定、管理者IDも指定します。

レビュー用の独立Cloud Runサービスに同じコードをデプロイし、テスト用DB・テストLINEチャネル・テストシートで確認してください。本番データや本番LINEでスモークテストを送信しないでください。標準`deploy.sh`は検証済みコミットを既存サービスに`--no-traffic`でデプロイするための最終手段です。タグ付きURLへのアクセスでも実データへ作用し得ることに注意してください。

## 切り替えの確認項目

- SQLite/PostgreSQLの回帰テスト、クリーン環境の依存インストール、署名付きWebhook。
- 仮予約・変更要求・通常取消・12時間以内/3時間以内の取消。
- 管理者通知の再送、既読/到達保証を仮定しない運用、スタッフ承認・却下。
- カレンダー障害、Sheets障害、同時受付、ユーザー返信失敗時の通知保存。
- DBとCalendarの重複表示、月間集計、同姓同名の照合。
- 新しいボタンの有効期限。旧ボタンは最新一覧を開き直す案内になる。
- `/health`は正常時200、異常時503。公開予約情報APIは401。
- 通知再送Schedulerを認証付きPOSTで設定。キャンセル待ちジョブは停止の意図確認後に設定変更・再開する。

スタッフが未処理要求を確認でき、旧データとの照合が終わってからトラフィックを切り替えます。切り替え前後に新しい受付を失わない時間帯・手順を決めてください。

## ロールバック

切り替え前のリビジョン名とDBバックアップを保存します。旧リビジョンへ戻すだけでは新DBに保存した仮予約を旧SQLiteへ戻せません。障害時は受付を停止して新DBの未処理要求を回収し、スタッフへ引き継いだ上で復旧します。DBの削除や上書きはしないでください。

## 自動配備の運用

`main`へのpushでは、1つのCloud Buildトリガーでビルドし、`--no-traffic --tag=review`でレビュー用リビジョンへ配備します。重複トリガーは停止しています。本番への昇格は、検証後に対象リビジョンを明示してトラフィックを切り替えます。旧SQLiteリビジョンへ戻すだけでは新DBの受付を参照できないため、そのまま戻さないでください。
